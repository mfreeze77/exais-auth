# Session-policy evidence review — 2026-09-08

**The session foundation remains unqualified.** Existing CDI 5.3 observations support a specific candidate/promotion sequence; the separate CDI 5.6 zero-grace observations expose a legitimate-race availability failure. Neither substitutes for maintained-SDK behavior through two replicas. The three Keycloak strict-profile failures remain failures of their stated expectations. This review changes no tests, baseline, ledger, configuration, or engine selection, and waives no requirement. It used local files only; no runtime, Docker, network or download action was performed. It is an implementation/evidence review, not the required independent security review.

## Binding constraints

`SES-003` requires atomic comparison/rotation of authoritative refresh verifiers and a documented, tested concurrency/response-loss state machine. `SES-004` requires a versioned distinction between allowed race/retry and stale replay, with intended-family revocation on confirmed compromise. Their original texts remain at `baseline/expert-auth-full-parity-plan-v1.0/registry/requirements.json:1752-1783`.

`baseline/expert-auth-full-parity-plan-v1.0/docs/SECURITY_ACCEPTANCE.md:35-54` requires two engine replicas sharing authoritative state, failure injection before commit, after commit before response, and after response transmission starts. Its invariant is **no two unrelated valid successor chains**, not exactly one HTTP 200. Lost-response behavior must follow a frozen retry/reuse policy; it does not demand successful recovery for every stale-token submission. It separately requires bounded online revocation, truthful offline residual acceptance, revocation/removal races, restart persistence, key/dependency failure behavior, correct transports and real frontend refresh coordination. These remaining cases cannot disappear because a narrower sequence passes.

The kickoff's binding foundation gate also requires representative Node/React and Python clients, refresh/reuse/revocation/cookie/header behavior, one authoritative engine-owned refresh state machine, and no duplicate adapter refresh store (`baseline/EXPERTAUTH_KICKOFF.md:45-65`). It prohibits stale evidence and acceptance weakening, and requires reviewed correction of genuine test defects (`baseline/EXPERTAUTH_KICKOFF.md:99-101`).

## What the current evidence proves and does not prove

| Core 12.2.0, CDI 5.3 | Two same-parent requests return `OK`; explicit stateful verification promotes the first selected child; sibling refresh returns `TOKEN_THEFT_DETECTED`; selected child's next refresh returns `OK`. | One selected ordering of raw private-Core calls. Promotion is serialized after both refresh responses, not raced. It does not exercise maintained-SDK error handling, frontend coordination, all candidate/descendant orderings, or crash persistence. |
| Core 12.2.0, CDI 5.3 response loss | The HTTP client receives response headers, closes without reading the token body, retries the parent on the other node, promotes the retry child, then sees parent replay rejected. | Actual response-body abandonment; not a before-commit crash or an instrumented after-commit/before-response fault. No partial-body delivery or SDK credential installation/rollback is exercised. |
| Core 12.2.0, CDI 5.6, grace 0, reuse action `TOKEN_THEFT` | Old-parent reuse returns theft, then online verification and descendant refresh are unauthorized. A simultaneous pair returns `OK`/`TOKEN_THEFT_DETECTED`, and the successful response's replacement becomes unauthorized. | Real strict-profile family revocation and lost availability. It does not qualify a positive-grace policy, a retry window, or response-loss recovery, and cannot be generalized to all Core versions/configurations. |
| Keycloak 26.7.3, `revokeRefreshToken=true`, max reuse 0 | Stale retry rejects and invalidates the replacement; a concurrent pair produces one 200 but its replacement is unusable; retry after a discarded successful response rejects. | Three retained failures of stronger recovery/child-survival expectations. They are not evidence that every supported engine mapping/configuration is impossible. The loss test receives the whole response and deletes its variable; it is application-level discard, not transport fault injection. |

The Core sequence and assertion boundaries are in `tests/foundation/oss_core_probe.py:238-283`, with results at `evidence/foundation/oss-core/results.json:221-250`. The 5.6 branch explicitly changes `self.cdi` and restores it afterward (`tests/foundation/oss_core_probe.py:400-433`); its separate outcomes are at `results.json:329-362`. The launcher declares both zero grace and `recent_token_reuse_behaviour: TOKEN_THEFT` at `tools/launch_oss_probe.py:49-50`. Those settings must accompany any claim; “5.6 fails refresh” would overstate this evidence.

The Core test correctly warns that a theft response does not prove adapter revocation (`oss_core_probe.py:258`). In fact it tests sibling theft and then selected-child success **without invoking a maintained SDK's theft callback/default error handler**. Whether that real handler subsequently revokes the shared handle, clears credentials, retries, or leaves the winning client usable is an open end-to-end question. An adapter that reacts differently can produce a different result from this raw-Core sequence. This review does not assume that behavior without source and live evidence.

The Core logout race has only one recorded ordering: racing refresh is already `UNAUTHORISED`, followed by another unauthorized refresh (`results.json:252-265`). It supports that ordering, not the unobserved case where a successful refresh response arrives after logout and overwrites cleared client credentials. The recorded 3.742 ms online-check duration is one request duration after revocation, not a propagation SLA (`oss_core_probe.py:223-233`). `checkDatabase=false` still calls Core and is not independent local JWT verification.

The Core harness returns exit 0 after recording failed/unavailable requirement outcomes; it returns nonzero for harness exceptions (`oss_core_probe.py:470-491`). `OSS56-GRACE0-RACE-OBSERVED` is deliberately `observed`, not passed (`:427-430`). Consequently neither exit 0 nor a total of passed rows clears SES-003/004 or M1. Existing `foundation_passed=false` and explicit claim limits must be preserved.

Keycloak's assertions require exactly one successful concurrent response, survival of the legitimate child after stale replay, and HTTP 200 on lost-response retry (`tests/foundation/keycloak_sessions.py:218-263`). These expectations are stricter than the baseline's policy-dependent wording. **Do not delete, rename away, or turn their existing failures into passes.** Any future correction must explicitly distinguish a characterization expectation from a binding invariant, preserve the original result, state the intended accepted/rejected retry cases before testing, and receive review under the kickoff. Merely choosing “always revoke on any duplicate” to avoid implementing required legitimate retry/coordination semantics is not a waiver of SES-004 or the supported SDK contracts. The shared parent `sid` is correctly not treated as a failure; client-specific revocation isolation and explicit global logout are separate cases (`keycloak_sessions.py:265-294`).

## Contract/version and maintained-SDK evidence still needed

The captured operation is **CDI-111 at CDI 5.3.0**, `POST /appid-<appId>/recipe/session/refresh`; verification is **CDI-115**, and the browser/SDK refresh surface is **FDI-032 at FDI 4.2.0**. See `contracts/api-contracts.json:71465`, `:73275`, and `:11454`. The capture still marks concurrency, side effects, exact-schema rights and runtime conformance unknown. A 5.6 experiment does not silently replace this captured contract or prove its compatibility. Retain every original ID and document any additional supported-version profile/delta separately.

The current Node test performs sequential refresh → protected request → logout and respects returned access-token headers (`examples/node-react/test/live.test.js:44-64`). Its cookie case tests missing-CSRF rejection, not concurrent successful cookie refresh (`:79-88`). Earlier Node failures and the distinction between its default hybrid verifier and the separate local-JWT route are preserved in `docs/test-corrections.md:3-18`. The actual browser report declares four password/cookie-session cases only (`evidence/browser/oss-password-05/results.json`); it supplies no multi-tab/refresh-race evidence.

The Python test also exercises sequential header/cookie refresh and logout (`tests/clients/python_probe.py:148-173`, `:217-230`). Its readiness case asserts a `cdi_required: 5.4` label, while the app checks that Core advertises 5.4 (`examples/python/app.py:65-76`); that is not an observed outbound SDK negotiation trace. Neither these Python cases nor the raw-Core 5.3 probe establishes the pinned Python SDK's complete transaction behavior. The corrected test cookie jar is documented in its report; it does not stand in for browser storage/coordination behavior.

For the parent's bounded two-replica SDK proof, the evidence must establish these concrete facts, without inventing another engine or expanding into unrelated capabilities:

1. **Actual supported profile:** exact unchanged SDK/package/source pins, Core/runtime identity, outbound negotiated `cdi-version` per SDK, effective grace/reuse policy and transport mode. Do not infer negotiation from a readiness label, source maximum, a test comment, or the top-level 5.3 report field. Do not force a protocol unsupported by the pinned SDK and describe that as unmodified-SDK qualification.
2. **Complete client transaction:** requests enter real maintained SDK refresh and verification middleware on both replicas; any promotion handshake, returned access/refresh/front-token/anti-CSRF values, and default/custom theft handling actually execute. Client state consumes responses as the selected cookie/header SDK does. Record sanitized token fingerprints/lineage or equivalent safe correlators, replica and event ordering—not raw tokens. A raw Core `TOKEN_THEFT_DETECTED` alone proves neither cookie clearing nor family revocation by the backend SDK.
3. **Race and retry outcomes:** distinguish allowed same-current-token races, candidate promotion/continuation, lost-response retry, and replay outside the accepted state/time window. Establish that permitted races converge without unrelated live successor chains; exercise late/reordered responses so an older result cannot overwrite usable or cleared credentials. For the representative React/browser case, run the maintained interceptor/tab coordination itself and record refresh request count, bounded retry behavior and final protected-request outcome. A manually coordinated HTTP client cannot qualify that frontend behavior.
4. **Commit/failure distinction:** label body discard as body discard. Before-commit, after-commit/before-response and partial-response cases need actual injection tied to observable transaction/transport boundaries; a sleep or deleting a response variable cannot prove them. Record authoritative state/credential outcomes after retry or restart according to the predeclared policy. If these boundaries cannot be exercised in the bounded run, retain them as unexecuted/blocked rather than inventing evidence.
5. **Real revocation consequence:** after accepted/rejected retries, prove the intended session/family's actual SDK refresh/online-verification outcome on both replicas, and separately measure the declared offline residual window. Preserve separate success/failure orderings for logout versus refresh. Existing single-sample results do not qualify a propagation bound, process restart, ban/membership-removal races or all original platform profiles.

These are evidence constraints for the existing session gate, not authorization to waive other foundation requirements or a new broad implementation plan. Any missing native/live-provider or independent-review qualification remains blocked; no policy review alone closes it.
